## Decisions Made

- **Go dependencies resolve from `go.mod`, not `go.sum`.** `go.sum` is not a
  lockfile — it hashes the entire module graph, every version the resolver ever
  considered. Measured across 28 consuming repositories: 5,263 findings came from
  it, and on one repo 148 of 148 Go findings named versions the build never
  selects (`x/net` flagged at a 2019 pseudo-version while the build uses v0.56.0).
  Consumers had responded by excluding `go.sum` outright, which left them with
  *zero* Go dependency coverage — a worse failure than the noise.

- **`go.sum` is still consulted, but only for what `go.mod` cannot answer.** Go
  1.17+ module graph pruning means `go.mod` names only modules providing imported
  packages; deeper transitives are linked but unnamed. For those, MVS selects the
  maximum required version, so the highest version in `go.sum` is the best
  available estimate — correct for 32 of 33 pruned modules when checked.

- **Only `go.sum` entries with a source hash count.** A `/go.mod`-only entry means
  Go fetched the module's metadata to compute the graph but never downloaded its
  code, so it cannot contribute a line to the build. This rule alone took mnemos
  from 53 residual false positives to 0.

- **Advisory detail is fetched per ID from `/v1/vulns/{id}`.** `/v1/querybatch`
  returns only `{id, modified}` — verified against the live API. Everything
  downstream had therefore been defaulting: every finding `medium`, empty summary,
  no CVE aliases, and the shipped fix-version remediation field (`c8d8e3b`) had
  never emitted anything, because it reads `Affected` which querybatch never
  returns. Deduplicated by ID, concurrency-bounded, and **fail-open**:
  under-reporting severity is bad, losing a finding is worse.

- **CVSS base scores are computed from the vector.** OSV publishes CVSS as vector
  strings; `cvssToSeverity` parsed floats only and its own comment concluded the
  score "is not embedded in the vector". True — but it is fully *determined* by it.
  Implemented CVSS v3.1 §8.1 including the scope-changed impact formula and the
  spec's integer round-up. v2/v4 vectors keep the conservative default rather than
  guessing.

- **Unreachable findings are demoted, never dropped.** OSV scopes Go advisories to
  import paths; those are now intersected with `go list -deps`. A provably
  unreachable finding becomes `info` with `reachable=false` and `affected_imports`
  recorded. Dropping it would be indistinguishable from a scanner that missed it,
  and reachability rests on a toolchain call that can be wrong. Conclusions only
  from positive evidence — no import metadata, or no enumerable build, leaves the
  finding untouched.

- **Reachability uses the toolchain, not static import parsing.** A vulnerable
  package is frequently reached *through* a dependency rather than imported
  directly; parsing the repo's own source cannot see that, and being wrong in that
  direction silently hides real vulnerabilities.

- **Released as v1.10.0 (minor).** Three features since v1.9.2 alongside the fixes.

## What Went Wrong

- **A real concurrency bug, caught by an existing test.** The first hydration
  implementation flattened the OSV results map, hydrated, then rebuilt it. Map
  iteration order is randomised, so advisories were reattributed to the wrong
  packages — `TestQueryOSV_BatchQuery` caught express's and lodash's swapped.
  Fixed by hydrating in place per package and never reassigning.

- **A second bug in the dangerous direction.** `go list -e` outside a module
  echoes the unresolved pattern (`./...`) and exits 0. Accepting that as a package
  would have turned "unknown" into a false "not linked" — silently suppressing
  real vulnerabilities. Caught by my own test; now filtered.

- **Two CVSS test expectations were wrong** (1.6/6.1 vs the correct 1.8/5.4) and
  had to be corrected to match the implementation. Normally a smell; defensible
  only because the canonical 9.8 and 10.0 vectors validate the formula
  independently, and the 6.1 turned out to be the scope-*changed* variant of the
  same vector (now covered as its own case).

- **Two existing tests encoded bugs and had to change.** `TestMapOSVSeverity`
  asserted that a CVSS vector maps to `medium`, and several fixtures used `go.sum`.
  Flagged explicitly in the PR rather than changed quietly.

- **`GO-2026-5932` was mischaracterised as a confirmed true positive** in the #248
  commit message, on the strength of a module@version match alone. It has
  `introduced: 0`, no fixed version, and is scoped to `x/crypto/openpgp` — a false
  positive for consumers linking `chacha20`/`cryptobyte`. The PR body carries an
  explicit retraction; **the commit message still carries the error** (amend would
  need a force-push).

- **Stacked PRs got no CI at all.** `ci.yml` triggers only on PRs targeting `main`,
  so #248 (based on #247's branch) ran nothing while GitHub reported
  `mergeable: CLEAN`. Retargeted to `main` to get real coverage. Same trap as a
  green-looking PR whose suite never ran.

- **`relicta notes` fails silently** — exit 1, no output, no error. Cause: AI is
  enabled in `.relicta.yaml` with `model: gpt-4` and the failure is swallowed;
  there is no `--no-ai` escape (the flag is opt-in `--ai`). The v1.10.0 changelog
  was written by hand.

- **`relicta approve` misreports the release** — shows `0.0.0` and `0 commits`
  while the state file correctly holds `1.10.0`. A display bug, but on the screen
  whose entire purpose is confirming what you are about to publish.

- **`relicta plan` pins `head_sha`**, so committing the changelog invalidated the
  plan. Had to re-plan (new run ID) to include it — the previous release's tag
  points at its own changelog commit, so that ordering matters.

## Open Questions

- Amend #248's commit message to remove the `GO-2026-5932` claim (force-push), or
  is the PR-body retraction enough?
- **11 of vorhut's 19 Go findings are `undetermined`** because those advisories
  carry no `ecosystem_specific.imports`. That is the ceiling on import-path
  scoping. Is there a better source, or is this simply OSV data coverage?
- Should reachability be opt-in? It shells out to `go list -deps` (60s bounded,
  `-mod=readonly`), which needs the toolchain and a warm module cache. Currently
  automatic and degrades to `undetermined`.
- CVSS v4 vectors fall back to `medium`. Worth implementing?
- Does `relicta`'s MCP server need pinning to a repo? It reported
  `current_version: 2.7.13` for nox (actually 1.9.2) — it was operating on some
  other working directory entirely.
